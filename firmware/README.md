# Firmware

STM32F401RE (NUCLEO-F401RE) application: receive telemetry lines on USART1,
show them on an SSD1306 OLED, append them to `telemetry.csv` on an SD card.

## What is in this directory - and what is not

| Path | Contents | Origin |
|---|---|---|
| `Core/Src/main.c` | Start-up, peripheral init, main loop | CubeMX layout; init functions **reconstructed** from the `.ioc` (see file header) |
| `Core/Src/telemetry.c`, `Core/Inc/telemetry.h` | Line parser, OLED view, SD logger | Project code |
| `drivers/user_diskio.c` | SD card over SPI for FatFs | Project code |
| `Core/Src/ssd1306*.c`, `Core/Inc/ssd1306*.h` | OLED driver | Third party: [afiskon/stm32-ssd1306](https://github.com/afiskon/stm32-ssd1306) (MIT) |
| `Core/Src/stm32f4xx_*.c`, `system_*.c`, `sys*.c`, `Core/Startup/` | HAL glue, start-up | Generated by STM32CubeMX (ST licence) |
| `STM32 Telemetry.ioc` | CubeMX project (MX 6.15.0, FW_F4 V1.28.3) | Project |
| `tests/` | PC-side unit tests with a simulated SD card | Project code |

**Not in the repository:** the STM32F4 HAL and CMSIS (`Drivers/`), FatFs
(`Middlewares/`), the generated FatFs glue (`FATFS/App/fatfs.c`, `fatfs.h`,
`ffconf.h`), the linker script and the CubeIDE project files. The firmware
therefore **cannot be built from a fresh clone alone** - generate the missing
parts from the `.ioc` first.

## Building (STM32CubeIDE - the supported route)

> These steps are written from the project structure, not from a recorded
> build log. TODO(verify on hardware): confirm and adjust on the next rebuild.

1. Install STM32CubeIDE (or STM32CubeMX 6.15+) with the STM32Cube FW_F4 V1.28.x package.
2. Open `firmware/STM32 Telemetry.ioc`, check the *Project Manager* tab
   (toolchain: STM32CubeIDE) and press **Generate Code**. This adds `Drivers/`,
   `Middlewares/`, `FATFS/`, the linker script and the IDE project files.
   `main.c` keeps its application calls because they sit inside
   `USER CODE` blocks. If the regenerated `SystemClock_Config()` /
   `MX_*_Init()` differ from the reconstructed ones, the generated code wins.
3. CubeMX creates an empty `FATFS/Target/user_diskio.c` template. Replace it
   with `drivers/user_diskio.c` (or exclude the template from the build and add
   `drivers/` as a source folder).
4. Enable float formatting for `snprintf`: *Project > Properties > C/C++ Build >
   Settings > MCU Settings > "Use float with printf from newlib-nano"*
   (`-u _printf_float`). Float **scanf** support is not needed - the parser uses
   `strtoul`/`strtof`.
5. Build and flash through the on-board ST-LINK.
6. Optional: exclude `Core/Src/ssd1306_tests.c` (demo code, unused).

## Building with make (untested)

`Makefile` targets `arm-none-eabi-gcc` and expects the layout produced by step 2
above. Without the vendor files it stops with an explanation instead of a
compiler error:

```bash
make            # needs Drivers/, Middlewares/, FATFS/, linker script
make flash      # st-flash
```

It has not been run against a real toolchain yet, which is also why CI does not
build the firmware (it runs static analysis and the host tests instead).

## Host tests (no hardware, no ARM toolchain)

```bash
make host-test          # or: make -C tests
```

`telemetry.c` and `user_diskio.c` are compiled for the PC with AddressSanitizer
and UBSan against small stand-ins for the HAL, FatFs and the OLED driver
(`tests/stubs/`):

* `test_telemetry` feeds bytes into the fake UART and checks parser, checksum
  handling, the text sent to the OLED, the CSV written to the "SD card", overrun
  handling and mount retry/back-off.
* `test_diskio` runs the SD driver against `sd_card_sim.c`, a behavioural model
  of an SDHC card in SPI mode (CMD0/8/55/41/58, single and multi block
  read/write, busy signalling, chip-select rules).

A simulated card is not a real card: timing, electrical behaviour and the
quirks of individual cards are not covered. Everything in
[`docs/FIRMWARE_AUDIT.md`](../docs/FIRMWARE_AUDIT.md) remains
**"needs hardware re-test"**.

## Runtime characteristics (by design, not measured)

* Super-loop, polling, no RTOS, no interrupts except SysTick; no DMA.
* One received line triggers a full OLED refresh and an open-append-sync-close
  cycle on the SD card, both blocking. Bytes arriving meanwhile are lost
  (detected through the UART overrun flag, the damaged line is dropped).
* System clock 16 MHz HSI (per `.ioc`); SD SPI clock 62.5 kHz during card
  initialisation, 8 MHz afterwards.
